# Payment Service

[![CI](https://github.com/ksdevks/payments-service/actions/workflows/ci.yml/badge.svg)](https://github.com/ksdevks/payments-service/actions/workflows/ci.yml)

Микросервис асинхронной обработки платежей: принимает платеж по HTTP, обрабатывает его через эмулятор платежного шлюза и уведомляет клиента через webhook. Стек: FastAPI, Pydantic v2, SQLAlchemy 2.0 (async), PostgreSQL, RabbitMQ (FastStream), Alembic, Docker Compose, uv.

## Быстрый старт

```bash
cp .env.example .env          # задайте API_KEY (минимум 16 символов)
docker compose up -d --build
docker compose ps             # migrate - exited (0), остальные - running/healthy
```

- API: <http://localhost:8000>, все эндпоинты требуют заголовок `X-API-Key`
- Swagger: <http://localhost:8000/docs>, если в `.env` задано `API_DOCS_ENABLED=true` (кнопка Authorize принимает ключ)
- RabbitMQ Management: <http://localhost:15672> (`payments` / `payments`)

Остановить и удалить данные: `docker compose down -v`.

## Примеры

```bash
export API_KEY=$(grep ^API_KEY= .env | cut -d= -f2)

curl -i -X POST http://localhost:8000/api/v1/payments \
  -H "X-API-Key: $API_KEY" \
  -H "Idempotency-Key: order-42" \
  -H "Content-Type: application/json" \
  -d '{
        "amount": "1250.50",
        "currency": "RUB",
        "description": "Order 42",
        "metadata": {"order_id": 42},
        "webhook_url": "https://merchant.example/hooks/payments"
      }'
```

```http
HTTP/1.1 202 Accepted
Location: /api/v1/payments/5b0c...
{"payment_id": "5b0c...", "status": "pending", "created_at": "2026-10-02T18:00:00Z"}
```

```bash
curl -s http://localhost:8000/api/v1/payments/<payment_id> -H "X-API-Key: $API_KEY"
```

| Ситуация | Ответ |
|---|---|
| Нет или неверный `X-API-Key` (любой эндпоинт, включая `/health/*`) | `401`, `{"code": "unauthorized"}` |
| Нет `Idempotency-Key` или невалидное тело | `422` |
| Повтор с тем же ключом и тем же телом | `202`, тот же платеж, заголовок `Idempotent-Replayed: true` |
| Тот же ключ, другое тело | `409`, `{"code": "idempotency_key_reused"}` |
| Платеж не найден | `404`, `{"code": "payment_not_found"}` |

Webhook приходит POST-запросом с телом `{"event": "payment.processed", "notification_id", "payment_id", "status", "amount", "currency", "processed_at"}` и заголовком `Idempotency-Key`, одинаковым для всех повторов доставки. Успехом считается любой ответ 2xx; тело ответа не читается.

## Архитектура

```
src/payments/
  domain/          сущность Payment, Money, переходы статусов; без зависимостей от фреймворков
  application/     use cases (CreatePayment, GetPayment, ProcessPayment) и порты
  infrastructure/  PostgreSQL (репозитории, UoW, outbox store), шлюз, webhooks
    messaging/     topology (очереди), publisher (outbox -> RabbitMQ), consumer, handler (политика)
  entrypoints/     api (FastAPI), consumer (FastStream), relay (отдельный процесс)
```

Зависимости направлены внутрь: домен не знает ни о чем, прикладной слой знает только о домене и портах, FastAPI, SQLAlchemy и FastStream живут на краях. Ошибки прикладного слоя переводятся в HTTP-коды в одном месте (`entrypoints/api/errors.py`).

Процессы в docker-compose:

| Сервис | Роль |
|---|---|
| `migrate` | `alembic upgrade head`, одноразовый; остальные ждут его успешного завершения |
| `api` | принимает запросы, пишет платеж и событие в outbox одной транзакцией; от RabbitMQ не зависит |
| `relay` | публикует события из outbox в RabbitMQ |
| `consumer` | обрабатывает `payments.new`: шлюз, статус, webhook, retry/DLQ |

## Поток обработки

1. `POST /api/v1/payments` в одной транзакции создает строку в `payments` и событие `PaymentCreated` в `outbox`.
2. Relay арендует пачку событий (`UPDATE ... FROM (SELECT ... FOR UPDATE SKIP LOCKED)`) и публикует их по одному с publisher confirms и `mandatory`. Каждое событие отмечается `published_at` сразу после подтверждения брокера.
3. Consumer получает событие, вызывает шлюз (2-5 с, 90% успех, 10% отказ банка), фиксирует статус, отправляет webhook и отмечает `webhook_delivered_at`.

## Гарантии доставки

**Outbox.** Платеж и событие о нем коммитятся атомарно, поэтому ситуации "платеж есть, события нет" не бывает. Публикация - at-least-once: если relay упадет между подтверждением брокера и отметкой `published_at`, событие уйдет повторно после истечения аренды.

**Успех публикации - только подтвержденная доставка в очередь.** Брокер создается с `publisher_confirms=True` и `on_return_raises=True`. Второй флаг принципиален: сообщение, которое RabbitMQ вернул из-за отсутствия привязки, все равно получает confirm, и без этого флага publish завершился бы успешно, а событие пропало бы. Интеграционный тест проверяет, что публикация без привязки падает.

**Аренда вместо долгой транзакции.** `next_attempt_at` служит одновременно расписанием повторов и арендой: строка захватывается короткой транзакцией, публикация идет вне ее, упавший relay не держит блокировки. Счетчик `attempts` увеличивается при каждом захвате и работает как fencing-токен: relay с истекшей арендой не может изменить строку, которую уже забрал другой. Каждый шаг relay ограничен общими дедлайнами: публикация - `PUBLISH_TIMEOUT`, операция с хранилищем целиком, включая ожидание соединения и коммит, - `DB_COMMAND_TIMEOUT`. Перед каждым шагом relay проверяет, что до конца аренды остается не меньше бюджета шага (сумма двух дедлайнов), и если нет, возвращает необработанный остаток пачки. При старте проверяется, что аренда вмещает хотя бы два шага.

**Идемпотентность на четырех уровнях.**
- API: уникальный индекс на `idempotency_key` и отпечаток тела запроса (sha256 канонизированного JSON). Корректность при гонке обеспечивает индекс, а не предварительная проверка.
- Шлюз: контракт порта `PaymentGateway` требует идемпотентности по `payment.id`, как у реальных платежных шлюзов с ключом идемпотентности. Эмулятор выполняет его так же, как провайдер: результат фиксируется в собственном журнале `emulated_gateway_charges` при первом обращении (`INSERT ... ON CONFLICT DO NOTHING`), повторы - параллельные, после рестарта, после смены `GATEWAY_SUCCESS_RATE` - получают зафиксированный результат без повторной обработки.
- Consumer: каждый шаг фиксируется отдельно, результат применяется под `SELECT ... FOR UPDATE`. Шлюз вызывается вне транзакции, поэтому при параллельной обработке дубля или сбое коммита после ответа шлюза он может быть вызван повторно. Однократность списания в этих случаях дает идемпотентность шлюза, а не блокировка в БД; оба сценария покрыты тестами, которые проверяют единственное списание, а не только единственную запись статуса.
- Webhook: `notification_id` детерминирован (uuid5 от платежа и статуса) и передается в `Idempotency-Key`, чтобы получатель мог дедуплицировать повторы.

Сквозная гарантия: **at-least-once + идемпотентные обработчики**. Exactly-once через распределенные транзакции не делается сознательно: это дорого и для задачи не нужно.

## RabbitMQ: retry и DLQ

Exchanges: `payments`, `payments.retry`, `payments.dlx` (все direct). Все очереди quorum. Маршруты:

```
payments -> payments.new                                    обычная доставка
payments.new -(временная ошибка)-> payments.retry -> payments.new.retry.1000ms
                                                  -> payments.new.retry.2000ms
payments.new.retry.<delay>ms -(TTL истек)-> payments -> payments.new
payments.new -(отказ, с диагностикой)-> payments.dlx -> payments.new.dlq
payments.new -(reject, нативный DLX)-> payments.dlx -> payments.new.dlq
```

- **3 попытки** - три обработки всего: первая и два повтора с задержками 1 и 2 секунды. Настраивается `MAX_DELIVERY_ATTEMPTS` и `RETRY_BASE_DELAY_MS`.
- **Своя очередь на каждую задержку.** RabbitMQ истекает сообщения только с головы очереди, поэтому одна общая очередь с TTL на сообщении давала бы head-of-line blocking. Задержка входит в имя очереди: смена настроек создает новые очереди, а не `PRECONDITION_FAILED`.
- **Надежное перемещение между очередями.** У classic-очередей dead-lettering выполняется без подтверждений и может потерять сообщение. Поэтому очереди quorum с `x-dead-letter-strategy=at-least-once` и `x-overflow=reject-publish`: сообщение покидает исходную очередь только после подтверждения целевой. Это касается возврата из retry-очередей и попадания в DLQ.
- **Номер попытки учитывает возвраты.** Номер обработки - это `x-attempt` из запланированной копии плюс `x-delivery-count`, который quorum-очередь ведет сама при `nack` с возвратом и при падении consumer'а до ack. Любая повторная доставка расходует общий бюджет из трех попыток. Сообщение, вернувшееся сверх бюджета, повторно не обрабатывается: если платеж уже завершен (последняя попытка прошла, а ACK потерялся), сообщение подтверждается, иначе уходит в DLQ. Семантика `x-delivery-count` описана для RabbitMQ 3.13, на котором зафиксировано окружение.
- **Сбой планирования повтора.** Если не удалось опубликовать копию в retry-очередь, consumer сам выдерживает положенную задержку (не больше наибольшей в политике) и возвращает сообщение через `nack`. Следующая доставка учитывается как следующая попытка, так что и бюджет, и экспоненциальная задержка сохраняются даже при сломанной retry-очереди. Это аварийный режим; штатный путь - TTL-очереди.
- **Диагностика в DLQ.** Отказ, обработанный политикой, публикуется в DLQ явно (confirm + mandatory) с заголовками `x-error-type`, `x-dead-letter-reason`, `x-attempt`, `x-original-queue`, `x-dead-lettered-at`. Все, что до политики не дошло (невалидное тело, превышен страховочный `x-delivery-limit`, сбой самой публикации в DLQ), попадает туда нативным dead-lettering с заголовком `x-death`: диагностика в этом случае только в логах, но сообщение не теряется.
- **Классификация ошибок.** Таймауты, сетевые сбои, сбой DNS, 5xx, 408, 425, 429 - временные, повторяются. Остальные 4xx от получателя, запрещенный адрес получателя, ненайденный платеж, нарушение доменного инварианта - сразу в DLQ. Неизвестные ошибки считаются временными: упавшая база должна ретраиться, а не терять платеж.
- **Отказ банка не ошибка.** 10% отказов шлюза - бизнес-результат: платеж получает статус `failed`, клиент получает webhook. Технический сбой шлюза - отдельная ошибка, она ретраится.
- **Тип очереди неизменяем.** RabbitMQ не меняет тип существующей очереди при повторном объявлении. Смена типа или аргументов в работающей системе делается через новые имена очередей, переключение публикации и дренирование старых.

## Webhook

- **Общий дедлайн.** Таймаут httpx ограничивает каждую фазу запроса отдельно, а чтение - паузу между порциями данных, а не весь ответ. Поэтому вся доставка, включая проверку адреса, обернута в `asyncio.timeout(WEBHOOK_TIMEOUT)`; истечение - временная ошибка.
- **Тело ответа не читается.** Запрос выполняется потоком, решение принимается по статусу. Медленное или огромное тело не держит consumer и не расходует память.
- **Защита от SSRF.** Перед отправкой хост резолвится, и все его адреса обязаны быть публичными: приватные, loopback, link-local (включая адрес метаданных облака `169.254.169.254`), CGNAT, multicast и зарезервированные диапазоны отклоняются, в том числе в IPv4-mapped IPv6. Исключения задаются явно в `WEBHOOK_ALLOWED_HOSTS`. Редиректы не выполняются.

## Решения и компромиссы

- **Отдельные ORM-модели и доменные сущности** с явным маппингом. Больше кода, но домен не зависит от SQLAlchemy, а инварианты продублированы CHECK-ограничениями в БД.
- **Ключ на всех эндпоинтах, включая health.** ТЗ требует `X-API-Key` везде; healthcheck в compose и пробы оркестратора передают заголовок. Swagger, ReDoc и `/openapi.json` выключены по умолчанию (страница Swagger не умеет передавать ключ при загрузке схемы) и включаются `API_DOCS_ENABLED=true`.
- **API не зависит от RabbitMQ.** Недоступность брокера не мешает принимать платежи: события копятся в outbox и уходят, когда брокер вернется.
- **Порядок событий не гарантируется.** Для независимых платежей он не нужен, а строгий порядок ограничил бы параллелизм relay.
- **Хранилище RabbitMQ в томе.** У брокера именованный том и фиксированный `hostname`: данные RabbitMQ привязаны к имени ноды. Без этого `docker compose down` и `up` сохранили бы платежи в PostgreSQL с отметкой "опубликовано", но потеряли бы сами сообщения.

## Известные ограничения

- **Аварийная пауза перед повтором живет в памяти процесса.** Если публикация в retry-очередь не удалась и consumer упал именно во время паузы, сообщение вернется раньше положенной задержки. Бюджет попыток при этом сохраняется (падение тоже увеличивает `x-delivery-count`), теряется только точность паузы. Устранение требует хранить расписание повторов в БД, для двойного отказа это неоправданно.
- **DNS rebinding.** Проверка адреса и подключение выполняют резолв по отдельности, и злонамеренный DNS может между ними вернуть другой адрес. Полная защита - подключение строго к проверенному адресу или egress-прокси с той же политикой.
- **Документация API при включенном флаге** доступна без ключа: это осознанный режим разработки, по умолчанию он выключен.
- **Диагностика нативного dead-lettering** (невалидное тело, превышен страховочный лимит доставок, сбой публикации в DLQ) есть только в `x-death` и логах consumer'а.
